Acceso y roles

El sistema usa autenticación JWT con tres roles. Cada empleado puede tener acceso solo a los módulos que le estén habilitados.

Roles

🛡️
Administrador
ROLE_ADMIN

Acceso total al sistema. Puede crear usuarios, asignar roles y módulos.

🔬
Empleado
ROLE_EMPLEADO

Accede solo a los módulos que el admin le habilitó. No puede gestionar usuarios.

🏢
Cliente
ROLE_CLIENTE

Ve únicamente su propio dashboard con sus análisis y puede descargar resultados.

Sesión y seguridad

  • El JWT expira en 1 hora (3 600 000 ms). Si una sesión queda inactiva, el usuario debe volver a ingresar.
  • Las contraseñas se almacenan con BCrypt, nunca en texto plano.
  • El endpoint /login devuelve el token, el rol y la lista de módulos habilitados.
  • La ruta /actuator/health es pública para los checks de Fly.io.

Seguridad

Flujo de login y autenticación JWT

El sistema usa autenticación stateless: no hay sesión en el servidor. Cada request lleva el token JWT en el header. Hay dos flujos distintos: el login inicial y la validación por request.

Clases involucradas

ClasePaqueteResponsabilidad
AuthController controller Endpoint POST /login. Orquesta el login y devuelve el token + datos del usuario.
JwtUserDetailsService service Implementa UserDetailsService de Spring. Busca el usuario por email (o username) y construye el objeto UserDetails con su rol.
JwtUtil security Genera y valida tokens JWT. Extrae claims (subject = email, userID). Firma con HMAC-SHA usando la clave de JWT_SECRET.
JwtRequestFilter security Filtro que se ejecuta en cada request. Extrae el Bearer token, lo valida y setea la autenticación en el SecurityContextHolder.
SecurityConfig configuration Configura Spring Security: rutas públicas, STATELESS session, CORS, HSTS, y registra el JwtRequestFilter antes del filtro estándar de Spring.
DaoAuthenticationProvider Spring Security Delega a JwtUserDetailsService para cargar el usuario y compara la contraseña con BCrypt.
JwtAuthenticationEntryPoint security Si un request protegido llega sin token o con token inválido, devuelve 401 Unauthorized.
UserRepository repository Acceso a la tabla CHEMI_USERS. Búsqueda por email o username.
UserService service Devuelve los módulos habilitados del usuario (getModulosForUser), que se incluyen en la respuesta del login.

Flujo 1: login inicial (POST /login)

1
Request del frontend

El frontend envía POST /login con email y password como @RequestParam (form params, no JSON).

2
AuthController.login()

Crea un UsernamePasswordAuthenticationToken con email y password, y lo pasa al AuthenticationManager.

3
DaoAuthenticationProvider

Llama a JwtUserDetailsService.loadUserByUsername(email) para obtener el usuario de la BD. Compara la contraseña ingresada con el hash BCrypt almacenado. Si no coincide, lanza BadCredentialsException → 401.

4
JwtUserDetailsService.loadUserByUsername()

Busca en CHEMI_USERS por email (y si no lo encuentra, por username). Construye un UserDetails con el email como principal y el rol como GrantedAuthority. Si el rol no tiene prefijo ROLE_, lo agrega automáticamente.

5
JwtUtil.generateToken()

Genera el JWT con: subject = email, claim userID = ID numérico del usuario, issuedAt = ahora, expiration = ahora + 1 hora. Firmado con HMAC-SHA256 usando la clave JWT_SECRET.

6
UserService.getModulosForUser()

Consulta USER_MODULOS para obtener los módulos habilitados para ese usuario.

7
Respuesta 200 OK

El controller devuelve un AuthResponse con: token, role, userId, username y modulos. El frontend guarda el token (típicamente en localStorage) y lo envía en cada request siguiente.

Payload del JWT

ClaimValorDescripción
subemail del usuarioIdentifica al usuario. Se usa como "username" en todo el contexto de Spring Security.
userIDLong (ID de BD)Claim custom. Los controllers lo usan para queries directas sin llamar a la BD solo para obtener el ID.
iattimestampFecha/hora de emisión.
exptimestampExpira 1 hora después de iat (configurable con jwt.expiration en ms).

Flujo 2: validación por request (requests protegidos)

1
Request con Authorization: Bearer <token>

Cualquier llamada a la API (ej: GET /api/estudios) debe incluir el header. Los requests OPTIONS (preflight CORS) se dejan pasar directamente sin validación.

2
JwtRequestFilter.doFilterInternal()

Se ejecuta antes que cualquier controller. Si la ruta es pública (ej: /login, /css/, .html), deja pasar sin validar. De lo contrario, extrae el token del header.

3
JwtUtil.extractUsername()

Parsea el JWT y extrae el sub (email). Si el token está mal firmado o expirado, la excepción se captura silenciosamente y username queda en null.

4
JwtUserDetailsService.loadUserByUsername()

Si se extrajo un username y el SecurityContextHolder no tiene autenticación previa, carga el UserDetails desde la BD para validar que el usuario sigue existiendo.

5
JwtUtil.validateToken()

Verifica que el email del token coincida con el del UserDetails y que el token no esté expirado.

6
SecurityContextHolder

Si el token es válido, crea un UsernamePasswordAuthenticationToken con el UserDetails y sus authorities, y lo setea en el contexto. Desde aquí, los controllers pueden usar @AuthenticationPrincipal o Authentication para obtener el usuario actual.

7
Continúa al controller

El request llega al controller correspondiente con la identidad ya resuelta. Si el token era inválido o faltaba, Spring Security retorna 401 Unauthorized via JwtAuthenticationEntryPoint.

Refresh de token

El endpoint POST /api/auth/refresh genera un nuevo token para la sesión activa. Requiere el token actual válido (el usuario ya debe estar autenticado). Útil para extender la sesión sin forzar un nuevo login.

Rutas públicas configuradas

Las rutas que no requieren JWT están definidas en dos lugares que deben mantenerse sincronizados:

ClaseListado
SecurityConfig POST /login, /actuator/health, OPTIONS /**, archivos estáticos (/*.html, /js/**, /css/**, /img/**, /fonts/**)
JwtRequestFilter /login, /authenticate, /api/auth, /actuator/health, /js/, /css/, /img/, /fonts/, extensiones .html .css .js .png .svg .ico .woff
Duplicidad de rutas públicas

Si agregás una nueva ruta pública, tenés que agregarla en los dos lugares: en SecurityConfig.securityFilterChain() y en las listas estáticas de JwtRequestFilter. Si solo la ponés en uno, puede fallar dependiendo del orden de los filtros.

CORS

La configuración CORS está centralizada en SecurityConfig.corsConfigurationSource(). Los orígenes permitidos se leen de la variable ALLOWED_ORIGINS (separados por coma). En desarrollo local el default es http://localhost:8080,http://localhost:63343.

Los requests OPTIONS (preflight del navegador) se permiten incondicionalmente para que no sean bloqueados antes de que CORS los procese.

Headers de seguridad

  • X-Frame-Options: DENY — previene clickjacking (la app no puede embeberse en un iframe)
  • Strict-Transport-Security — fuerza HTTPS con includeSubDomains por 1 año
Inicio

Dashboard

Hay dos dashboards según el rol del usuario logueado.

Dashboard de empleado / admin

Muestra un resumen del estado operativo del laboratorio:

  • Cantidad de estudios por estado (PENDIENTE, EN_PROCESO, COMPLETO, DEMORADO, CANCELADO)
  • Actividad reciente del día
  • Acceso rápido a los módulos habilitados

Dashboard de cliente

El cliente ve solo sus propios análisis. Puede:

  • Ver el listado de sus estudios con fechas y estado
  • Descargar el resultado (PDF de informe) cuando el estudio está completado
  • No tiene acceso a ningún otro módulo
Estado DEMORADO

Si la fecha de entrega de un estudio ya pasó y sigue en estado PENDIENTE o EN_PROCESO, el sistema lo marca automáticamente como DEMORADO cuando se consulta el listado general (GET /api/estudios/all).

Módulo principal

Muestras y análisis

Es el corazón del sistema. Registra cada estudio de análisis, asigna los parámetros a analizar con sus resoluciones y límites reglamentarios, y hace seguimiento desde el ingreso hasta la entrega del informe.

Estados de un estudio

PENDIENTE → EN_PROCESO → COMPLETO

También puede tener estado:

  • DEMORADO — asignado automáticamente si pasó la fecha de entrega
  • CANCELADO — cancelado manualmente, puede incluir motivo

Flujo de creación de un estudio

1
Crear el estudio

Se define: cliente, tipo de análisis, matriz, punto de muestreo, tipo de muestra, fecha de ingreso y fecha de entrega estimada. Se puede asociar a una sucursal del cliente.

2
Asignar parámetros y resoluciones

Se seleccionan los parámetros a analizar y las resoluciones reglamentarias aplicables (ej: Res 336/06, CAA). El sistema guarda un snapshot de los límites reglamentarios en ese momento.

3
Análisis por los técnicos

Cada analista ve los parámetros asignados en su Cola de análisis y va cargando resultados. El sistema manda email automático cuando se crea el estudio.

4
Cargar resultados

Cada parámetro tiene un campo de valor numérico o textual, metodología usada y observaciones. Se guarda en ANALISIS_PARAMETRO.

5
Generar informe PDF

Desde el estudio se puede generar el informe oficial con logo, resultados, comparación con límites reglamentarios, conclusión automática y nota de arsénico si corresponde.

6
Archivar el PDF en Supabase

Los archivos se suben al bucket de Supabase Storage. El cliente puede descargarlo desde su dashboard cuando el estado sea COMPLETO.

Número de protocolo

El número de protocolo se asigna automáticamente usando el numerador NUMERO_PROTOCOLO. Es un contador global con lock pesimista que garantiza que no se dupliquen aunque haya acceso concurrente. Se puede ver y ajustar manualmente desde el módulo Panel técnico → Numeradores.

Archivos adjuntos

Un estudio puede tener múltiples PDFs adjuntos (muestras físicas digitalizadas, informes previos, etc.). Se suben a Supabase Storage y quedan asociados al analisis_id.

Importante: snapshot de límites

Al asignar parámetros a un estudio, el sistema copia los límites reglamentarios actuales en la tabla ANALISIS_PARAM_LIMITE. Si después modificás los límites en el Panel Técnico, los estudios ya creados NO se ven afectados.

Analistas

Cola de análisis

Cada analista ve su propia cola: los parámetros que le fueron asignados en todos los estudios activos. Puede avanzar el estado de cada uno a medida que trabaja.

Estados de un ítem en la cola

PENDIENTE → EN_CURSO → ANALIZADO → REVISADO

Vistas disponibles

  • Mi cola — parámetros asignados al usuario logueado, de todos sus estudios activos
  • Mi cola (todos) — ídem pero incluye también los que no están en estado activo
  • Cola global — vista admin: la cola completa de todos los analistas
Email automático

Cuando se crea un nuevo estudio y se asignan parámetros, el sistema manda automáticamente un email a cada analista responsable mediante Brevo. El email indica el nombre del estudio y los parámetros asignados.

Documentación oficial

Generación de informes PDF

El sistema genera informes PDF con el formato oficial del laboratorio: logo, datos del cliente, resultados de cada parámetro comparados con los límites reglamentarios, y una conclusión automática.

Contenido del informe

  • Encabezado con logo de Chemiconsult y datos del laboratorio
  • Datos del cliente y punto de muestreo
  • Número de protocolo y fechas
  • Tabla de resultados por parámetro (valor, unidad, metodología, límites, si cumple)
  • Si hay más de una resolución aplicable, se muestran superíndices para identificar cada una
  • Conclusión automática (si todos los parámetros cumplen o cuáles no)
  • Nota especial de arsénico si corresponde (límite CAA)
  • Pie de página con certificaciones

Grupos de informe

Los parámetros se organizan en grupos dentro del informe (ej: "Físicoquímicos", "Microbiológicos"). Estos grupos se configuran desde GET/POST /api/grupos-informe con un código, etiqueta y orden de aparición.

Flujo de generación

  1. Ir al estudio terminado
  2. Hacer POST /api/estudios/{id}/generar-informe
  3. El sistema genera el PDF con OpenPDF y lo sube automáticamente a Supabase
  4. El archivo queda disponible para descarga desde el estudio y desde el dashboard del cliente
Parámetro tipoAnalisis

Cada parámetro tiene un tipoAnalisis (ej: FISICOQUIMICO, MICROBIOLOGICO). El informe usa este campo para agrupar los resultados en secciones separadas.

Módulo · clientes.html

Clientes

CRM del laboratorio: personas físicas y empresas con sus sucursales y contactos. Cada cliente puede recibir acceso al portal con ROLE_CLIENTE. Las bajas son siempre lógicas — nunca se borra físicamente un cliente.

Clases involucradas

ClasePaqueteResponsabilidad
ClienteController controller Endpoints CRUD de clientes bajo /api/clientes. Incluye /todos, /mi-cliente, /desactivar, /reactivar y /asignar-usuario.
ClienteSucursalController controller Endpoints de sucursales bajo /api/clientes. GET /{clienteId}/sucursales, POST/PUT /sucursales, PATCH /sucursales/{id}/desactivar. Sin DELETE.
ClienteContactoController controller Endpoints de contactos. GET por cliente o por sucursal, POST/PUT /contactos, PATCH /contactos/{id}/desactivar. Sin DELETE.
ClienteService service Alta con validaciones de unicidad (email, CUIT, DNI). Lógica de soft delete, reactivación y flujo de asignar usuario.
ClienteSucursalService service CRUD de sucursales. getSucursalesPorCliente() filtra siempre por activo=true. Solo desactivar, sin eliminación física.
ClienteContactoService service @Transactional en crear y actualizar. Maneja la vinculación M:N con sucursales mediante ClienteSucursalContactoDE.
ClienteDE entity Tabla CLIENTES. Polymórfico: campos de persona física y empresa en la misma fila (single table). Relación @OneToOne nullable con UserDE.
ClienteSucursalDE entity Tabla CLIENTE_SUCURSAL. @JsonIgnore en la referencia al cliente para evitar serialización circular. Tiene @OneToMany contactosAsociados (junction) con cascade ALL.
ClienteContactoDE entity Tabla CLIENTE_CONTACTO. @JsonIgnore en referencia al cliente. Tiene @OneToMany sucursalesAsociadas (junction) con cascade ALL y orphanRemoval.
ClienteSucursalContactoDE entity Tabla junction CLIENTE_SUCURSAL_CONTACTO. Tiene @ManyToOne a sucursal y @ManyToOne a contacto. Representación de la relación M:N.

Modelo de datos

La jerarquía completa de un cliente:

1
ClienteDE — un registro por cliente (persona o empresa), con campo activo y relación @OneToOne nullable a UserDE.
2
ClienteSucursalDE — cada ubicación física del cliente. Un cliente puede tener N sucursales. Solo se muestran las activo=true.
3
ClienteContactoDE — personas de contacto del cliente. Un contacto puede estar asociado a múltiples sucursales (M:N), modelado con ClienteSucursalContactoDE.

Tipos de cliente

TipoCampos únicosCampos comunes
PERSONA_FISICA nombre, apellido, DNI, CUIL, condiciónIVA email, teléfono, celular, dirección, localidad, provincia (enum), condiciónIVA
EMPRESA razón social, CUIT, condiciónIVA

El tipoCliente se fija al crear el registro y no se puede cambiar en edición. En el frontend, los radio buttons se bloquean (disabled) al abrir el modal de edición.

Validaciones en el alta

ClienteService.createCliente() verifica antes de persistir:

  • Email único (case-insensitive) — lanza excepción si ya existe otro cliente con ese email
  • CUIT único — solo aplica a EMPRESA
  • DNI único — solo aplica a PERSONA_FISICA

Si alguna validación falla, el servicio lanza una excepción que el frontend muestra en un toast de error.

Soft delete y reactivación

Los clientes nunca se eliminan físicamente. El campo activo: Boolean controla la visibilidad:

EndpointComportamiento
GET /api/clientesSolo clientes con activo=true
GET /api/clientes/todosTodos, incluyendo inactivos (usado por el frontend de clientes.html)
PATCH /api/clientes/{id}/desactivarSetea activo=false
PATCH /api/clientes/{id}/reactivarSetea activo=true
DELETE /api/clientes/{id}Eliminación física — solo para datos de prueba/error, no uso normal

Lo mismo aplica a sucursales y contactos: solo tienen PATCH /desactivar, sin DELETE.

Asignar acceso al sistema

Un cliente puede recibir acceso al portal (ROLE_CLIENTE) para ver sus propios análisis. El flujo es:

1
Admin hace click en "Asignar usuario" en la fila del cliente (solo visible si el cliente aún no tiene usuario y está activo).
2
Modal pide contraseña (mínimo 6 caracteres, con confirmación). El email que se usa es el del cliente — ya está cargado en el registro.
3
PATCH /api/clientes/{id}/asignar-usuario → ClienteService.asignarUsuario(). Valida que el cliente no tenga ya un usuario y que el email no esté registrado. Crea un UserDE con ROLE_CLIENTE, hashea la contraseña con BCrypt y vincula el usuario al cliente con @OneToOne.
Vista propia del cliente logueado

GET /api/clientes/mi-cliente usa @AuthenticationPrincipal para obtener el email del token JWT, busca el UserDE y desde ahí resuelve el ClienteDE via findByUser_Id(). Solo disponible para usuarios con ROLE_CLIENTE.

Sucursales

Cada sucursal tiene: nombre (requerido), dirección, localidad, provincia y activo. La API solo devuelve las activas en GET /{clienteId}/sucursales. En el frontend, al desactivar una sucursal el icono es un tacho de basura pero la acción llama a PATCH /sucursales/{id}/desactivar — no borra nada.

Contactos y vinculación M:N con sucursales

Un contacto (nombre, email, teléfono) puede estar asignado a una o varias sucursales del mismo cliente. Esto se persiste en la tabla junction CLIENTE_SUCURSAL_CONTACTO.

Al actualizar un contacto, el servicio usa un patrón de dos pasos dentro de @Transactional:

  1. Limpia todas las asociaciones actuales → sucursalesAsociadas.clear() + flush()
  2. Re-vincula las sucursales del nuevo request → llama vincularSucursales()

El flush forzado antes de re-insertar evita constraint violations en la junction table.

@JsonIgnore en entidades relacionadas

ClienteSucursalDE y ClienteContactoDE tienen @JsonIgnore en su referencia al ClienteDE padre. Sin ese annotation, Jackson entraría en un ciclo infinito al serializar (ClienteDE → sucursales → ClienteDE → ...) y la API devolvería un error 500 o un JSON truncado.

Frontend — comportamiento clave

FunciónComportamiento
cargarClientes() Llama a /api/clientes/todos (con inactivos). Guarda todo en memoria en todosLosClientes[] y ejecuta buscarClientes().
buscarClientes() Filtrado 100% client-side por texto libre (nombre/email/CUIT/DNI), tipo de cliente y estado activo/inactivo. No llama a la API. Resetea a página 1.
abrirModalAlta() Limpia el formulario, habilita los radio de tipo, setea clienteEditandoId = null.

Paginación Client-side con ITEMS_POR_PAGINA (default 5, configurable por dropdown). Los botones de página se renderizan dinámicamente según el total filtrado.

Configuración

Panel técnico

Configura toda la estructura reglamentaria del laboratorio: matrices de análisis, resoluciones aplicables, parámetros, metodologías y los límites máximos/mínimos de cada norma.

Estructura jerárquica

1
Matriz

Tipo de muestra a analizar (ej: Agua subterránea, Efluente industrial, Agua de red, Suelo).

2
Resolución

Norma reglamentaria asociada a una matriz (ej: Res 336/06, Res 283/19, CAA, Ley 19587). Puede o no tener destinos.

3
Destino

Uso al que se destina el agua (ej: Consumo humano, Riego, Bebida de animales). Solo en resoluciones que tienen destino (tieneDestino=true).

4
Parámetro en resolución/destino

Cada parámetro dentro de una norma tiene: tipo de límite (MAX, MIN, RANGO, TEXTO, AUSENCIA), los valores del límite, y la metodología estándar.

Tipos de límite

TipoCómo se evalúa

Módulo · task.html

Tareas

Tablero kanban para gestionar el trabajo interno del equipo. Las tarjetas se mueven entre columnas arrastrándolas. Soporta asignación a usuarios, fechas límite con alerta de vencimiento, archivado y email automático al asignar.

Clases involucradas

ClasePaqueteResponsabilidad
TaskController controller Endpoints REST bajo /api/task. Loguea cada operación con Log4j2.
TaskService service Lógica de negocio: creación, cambio de estado, archivado batch, email de asignación. Inyecta BrevoEmailService para notificaciones.
TaskDE entity Entidad JPA mapeada a la tabla TASK. Tiene relación @ManyToOne con UserDE.
TaskRepository repository Spring Data JPA con tres queries derivadas: por archived=false, por archived=true y por archived=false AND status.
TaskMapper mapper Conversión entre TaskDE y TaskTO. También contiene applyStatus() que maneja el completedDate automático.
TaskStatusEnum enums Los cuatro estados posibles: TODO, IN_PROGRESS, EN_REVISION, DONE.
BrevoEmailService brevo/service Envía el email HTML de asignación. Se llama desde TaskService.notificarAsignacion().

Transfer Object

CampoTipoNotas
idLongGenerado por la BD.
titleStringRequerido.
descriptionStringOpcional. Máx 1000 caracteres.
statusStringNombre del enum como string ("TODO", etc.). Default TODO.
userIdLongID del usuario asignado. Null si no tiene asignado.
userNameStringUsername del asignado, resuelto en el mapper. Lo usa el front para el avatar y el nombre.
dueDateLocalDateFecha límite opcional.
completedDateLocalDateSe setea automáticamente al pasar a DONE, y se limpia si vuelve a otro estado.
archivedbooleanSi está en el historial o en el tablero activo.
archivedDateLocalDateFecha de archivado. Se limpia si se restaura.

Columnas del tablero y estados

TODO → IN_PROGRESS → EN_REVISION → DONE

El movimiento no es lineal forzado: se puede arrastrar una tarjeta a cualquier columna desde cualquier otra. La única restricción es que el estado solo cambia arrastrando — el modal de edición no muestra el selector de estado.

Cambio de estado: drag & drop

Al soltar una tarjeta en otra columna, el JS llama:

PUT /api/task/{id}/status?status=IN_PROGRESS

En el backend, TaskMapper.applyStatus() maneja el efecto secundario:

  • Si el nuevo estado es DONE → setea completedDate = hoy
  • Si el nuevo estado es cualquier otro → limpia completedDate = null

El frontend actualiza el objeto en el array tasks[] en memoria con la respuesta del servidor y vuelve a renderizar el tablero, sin recargar todo.

Crear una tarea

1
Modal "Nueva tarea"

Al abrir el modal, el select de asignado se pre-rellena con el usuario logueado (userId de localStorage). Siempre se puede cambiar.

2
Estado inicial seleccionable

Al crear una tarea se puede elegir en qué columna aparece (radio buttons: Pendiente / En progreso / En revisión / Finalizada). En edición, esta sección se oculta.

3
POST /api/task → TaskService.createTask()

Si viene un userId, resuelve el UserDE desde la BD y lo setea en la entidad. Setea createdDate = hoy. Guarda y devuelve el TaskTO completo con userName resuelto.

4
Email de asignación

Si la tarea tiene asignado, notificarAsignacion() manda un email HTML al usuario con asunto "Nueva tarea asignada", el título y la descripción.

Editar una tarea

PUT /api/task/{id} actualiza título, descripción, asignado y fecha límite. El estado no se toca — eso solo cambia por drag & drop. La lógica de re-asignación:

  • Si el userId nuevo es distinto al anterior → manda email "Tarea reasignada a vos"
  • Si el asignado es el mismo → no manda email
  • Si se quita el asignado (userId = null) → no manda email
userName en el TO

El TaskTO incluye userName resuelto desde la relación TaskDE.user. El frontend lo usa para el avatar y el nombre en la tarjeta. Si no estuviera resuelto en el mapper, el frontend mostraría el avatar del usuario logueado en vez del asignado real.

Archivado

Archivar no elimina — setea archived = true y archivedDate = hoy. Las tareas archivadas no aparecen en el tablero principal (findByArchivedFalse()) pero sí en el modal de historial (findByArchivedTrue()).

OperaciónEndpointComportamiento
Archivar una tarea PUT /api/task/{id}/archive Solo disponible desde el botón de la tarjeta cuando está en columna DONE. Setea archived=true, archivedDate=hoy.
Archivar todas las DONE PUT /api/task/archive-all-done Batch: busca todas con archived=false AND status=DONE y las archiva en una sola operación. Devuelve 204 (sin body).
Ver archivo GET /api/task/archived Solo se llama cuando el usuario abre el modal "Archivo" (lazy load). El frontend pagina de a 8 en memoria.
Restaurar PUT /api/task/{id}/restore Setea archived=false, limpia archivedDate. La tarea vuelve al tablero en su columna original (el status no cambia).
Restaurar desde el archivo ajusta la paginación

Al restaurar una tarea, el JS elimina del array local y verifica si la página actual quedó vacía (si es la última y el item era el único). En ese caso decrementa archivedPage antes de re-renderizar para no mostrar una página vacía.

Eliminar una tarea

DELETE /api/task/{id} es una eliminación física. El service verifica que exista antes de borrar (lanza excepción si no). El frontend muestra un diálogo de confirmación (UI.confirmar()) antes de llamar al endpoint.

Filtro por usuario

La barra de filtros se genera dinámicamente a partir del array usuarios[] cargado de GET /api/users/asignables. Hay un botón por cada usuario asignnable, más "Todos" y "Sin asignar". Al filtrar, el JS aplica/quita la clase kb-hidden a las tarjetas — no llama a la API. Los contadores de columna siguen mostrando el total real, no el filtrado.

Badge de fecha límite

La función deadlineBadge(dueDate) calcula la diferencia entre hoy y dueDate y muestra:

CondiciónBadge
Fecha pasadaVencida · dd/mm/aa
HoyHoy

Dentro de 2–7 díasEn N días

Apertura automática via URL

Si la URL tiene el parámetro ?nueva=1 (ej: desde un link en otro módulo), el tablero abre automáticamente el modal de nueva tarea al cargar la página.

Flujo frontend — carga inicial

  1. cargarUsuarios() — GET /api/users/asignables — puebla el select de asignado y genera los filtros de la barra
  2. loadTasks() — GET /api/task — devuelve solo las no archivadas — guarda en tasks[]
  3. renderBoard() — distribuye las tarjetas en las cuatro columnas y actualiza los contadores
  4. setupDropzones() — registra los listeners de drag & drop en cada columna
  5. El modal de archivo se carga lazily solo cuando el usuario lo abre (show.bs.modal)
Módulo · usuarios.html

Usuarios

Gestión de todos los usuarios del sistema: alta de empleados, edición de perfil, cambio de contraseña, permisos de módulos y eliminación. Accesible para roles ROLE_IT y ROLE_EMPLEADO con el módulo USUARIOS habilitado.

Clases involucradas

ClasePaqueteResponsabilidad
UserController controller Endpoints REST bajo /api/users. Un método por operación.
UserService service Lógica de negocio: validaciones, hash de contraseñas, gestión de módulos. Usa PasswordEncoder (BCrypt) inyectado.
UserDE entity Entidad JPA mapeada a CHEMI_USERS. El campo password tiene @JsonProperty(WRITE_ONLY) — nunca se serializa en respuestas.
UserRepository repository Spring Data JPA. Métodos de búsqueda por email, username y por lista de roles.
UserMapper mapper Convierte entre UserDE y UserTO. Nunca incluye el password en el TO de salida.
JwtUserDetailsService service Comparte la búsqueda por email/username con UserRepository. Lo usa tanto el login como el filtro JWT.

Transfer Objects

TOCamposCuándo se usa
UserTO id, username, email, rol, modulos Respuesta de todos los endpoints GET y POST. Nunca incluye password.
UserCreateTO username, email, password, rol Body de POST /api/users (crear empleado). Incluye password en texto plano — el service lo hashea antes de guardar.
UserPerfilTO username, email Body de PUT /api/users/{id}. Solo edita nombre y email — nunca toca el password.
CambiarPasswordTO passwordActual, passwordNueva Body de PUT /api/users/{id}/password. Requiere la contraseña actual para verificar.

Pantalla: tabla de usuarios

Al cargar la página, usuarios.js llama a GET /api/users y guarda todos los usuarios en memoria (todosLosUsuarios). El filtrado y la paginación ocurren en el cliente, sin llamadas adicionales a la API.

getUsers() excluye los clientes

El service filtra explícitamente los usuarios con ROLE_CLIENTE antes de devolver la lista. Los usuarios clientes no aparecen en la pantalla de gestión de empleados. Para verlos hay que ir al módulo Clientes.

Operación: crear usuario

1
Validación en el frontend

El JS valida: nombre no vacío, email no vacío, contraseña de al menos 6 caracteres, y que las dos contraseñas coincidan. Si algo falla, muestra el error inline sin llamar a la API.

2
POST /api/users → UserController.createEmpleado()

Recibe el UserCreateTO con todos los campos incluyendo la contraseña en texto plano.

3
UserService.createEmpleado()

Verifica que no exista otro usuario con el mismo email (existsByEmail). Valida longitud de contraseña (≥ 6). Hashea la contraseña con BCrypt. Setea createdDate = hoy. Guarda en CHEMI_USERS.

4
Respuesta 201 Created

Devuelve el UserTO del usuario creado (sin password). El frontend recarga la lista completa y muestra un toast de éxito.

Operación: editar perfil

El modal de edición oculta los campos de contraseña — solo permite cambiar username y email. En el backend, UserService.updatePerfil() verifica que el nuevo username no esté ya en uso por otro usuario antes de guardar. El rol no se puede cambiar desde la edición de perfil.

El rol no se actualiza en PUT /{id}

UserPerfilTO solo tiene username y email. No hay endpoint para cambiar el rol de un usuario existente — habría que hacerlo directamente en la base de datos o agregar un endpoint nuevo.

Operación: restablecer contraseña (admin)

PATCH /api/users/{id}/reset-password permite a un admin poner una contraseña nueva sin conocer la actual. Valida longitud ≥ 6, hashea con BCrypt y actualiza UPDATE_DATE. El usuario afectado no recibe notificación automática (no hay email de reset).

Operación: cambio de contraseña propio

PUT /api/users/{id}/password es para que el propio usuario cambie su contraseña. Requiere la contraseña actual (passwordActual) y la valida con passwordEncoder.matches() antes de aplicar el cambio.

Operación: permisos de módulos

1
Abrir modal de permisos

El botón de permisos solo aparece para empleados — los IT no lo tienen porque reciben todos los módulos automáticamente.

2
Lista de módulos con checkboxes

El modal genera un checkbox por cada clave de MODULOS_LABELS en el JS. Los módulos ya habilitados aparecen marcados (leídos del cache local, no hay llamada extra a la API).

3
PUT /api/users/{id}/modulos → UserService.setModulos()

Recibe un Set<ModuloEnum>. Limpia los módulos actuales y reemplaza con el conjunto nuevo. Actualiza UPDATE_DATE.

4
Cache local actualizado sin refetch

Tras guardar, el JS actualiza el objeto en todosLosUsuarios directamente (u.modulos = modulos) sin recargar desde la API. La lista se mantiene actualizada.

ROLE_IT siempre tiene todos los módulos

UserService.getModulosForUser() retorna EnumSet.allOf(ModuloEnum.class) para cualquier usuario con rol ROLE_IT o IT, sin consultar USER_MODULOS. Por eso el botón de permisos no aparece para IT en el frontend.

Operación: eliminar usuario

DELETE /api/users/{id} llama a userRepository.deleteById(id) — es una eliminación física, no hay soft delete. El registro se borra de CHEMI_USERS permanentemente.

Eliminar un usuario cliente puede generar inconsistencias

Si el usuario eliminado está vinculado a un registro de CLIENTES (via user_id), el cliente queda con user_id = null pero el registro de cliente persiste. El frontend ya advierte esto en el modal de confirmación. Si necesitás eliminar un cliente, hacelo desde el módulo Clientes (desactivar, no eliminar).

Usuarios asignables

GET /api/users/asignables devuelve solo los usuarios con roles ROLE_EMPLEADO, ROLE_IT, EMPLEADO o IT. Lo usan los dropdowns de "responsable" en Agenda y Tareas. Los clientes y admins no aparecen en esos selects.

Flujo frontend — carga y filtrado

  1. cargarUsuarios() — GET /api/users, guarda en todosLosUsuarios[]
  2. buscarUsuarios() — filtra en memoria por texto (nombre o email) y por rol, guarda en usuariosFiltrados[]
  3. renderTabla() — pagina usuariosFiltrados y construye el HTML de la tabla
  4. renderPaginacion() — genera los botones de página según el total filtrado

El tamaño de página es configurable (5/10/15/20) desde el select del footer. El cambio de página o de tamaño vuelve a llamar solo a renderTabla(), sin ir a la API.

El sistema es un monolito Spring Boot que sirve tanto la API REST como el frontend estático.

Esquema de base de datos

Las migraciones se aplican automáticamente al iniciar (ddl-auto=update + data.sql). El archivo data.sql contiene tanto la definición de estructuras como los datos semilla iniciales. Para producción hay un archivo adicional seed_produccion.sql con los datos maestros (parámetros, resoluciones, matrices).

Hikari pool en producción

El pool está limitado a 5 conexiones máximas. Fly.io usa la instancia mínima (1 CPU, 1 GB RAM). Si hay errores de conexión en picos de carga, este es el primer parámetro a revisar.

Operaciones

Deploy en Fly.io

El sistema está desplegado en Fly.io, región São Paulo (gru). El deploy es via Docker: el Dockerfile hace un build de Maven y luego copia el JAR a una imagen JDK 21.

Infraestructura

  • App: chemiconsult-api
  • Región: gru (São Paulo)
  • Recursos: 1 CPU compartida · 1 GB RAM
  • Puerto: 8080 (interno) · HTTPS forzado (externo)
  • Auto-stop: la máquina se apaga si no hay tráfico (auto_stop = "stop"). Se enciende automáticamente al primer request.
  • Mínimo en ejecución: 1 máquina

Comandos de deploy

# Instalar Fly CLI
curl -L https://fly.io/install.sh | sh

# Login
fly auth login

# Deploy (desde el directorio con fly.toml)
fly deploy

# Ver logs
fly logs

# SSH a la máquina
fly ssh console

# Ver estado de la app
fly status

Variables de entorno en Fly.io

# Establecer un secreto
fly secrets set JWT_SECRET=mi_clave_secreta

# Establecer varios a la vez
fly secrets set DB_URL=jdbc:... DB_USERNAME=usuario DB_PASSWORD=clave

# Ver secretos (solo nombres, no valores)
fly secrets list

Health check

El endpoint GET /actuator/health es público y lo usa Fly.io para verificar que la app está levantada. También muestra el estado de la conexión a la base de datos (db: UP/DOWN).

Tip: primer request lento

Si la app estuvo sin tráfico, el primer request puede demorar ~5-10 segundos mientras la máquina arranca. Es comportamiento normal con auto_stop_machines = "stop". Si esto molesta, se puede cambiar a "suspend" para arranques más rápidos.

Build de Maven (Dockerfile)

El Dockerfile es un build en dos etapas:

  1. Stage 1: imagen Maven → mvn clean package -DskipTests
  2. Stage 2: imagen JDK 21 slim → copia el JAR y define ENTRYPOINT

El perfil de Spring activo en producción es prod, que carga application-prod.properties.
